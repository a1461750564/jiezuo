# 存量项目：先诊断，再选择改造强度

先定位实际 checkout、设计规范、tokens、组件、数据来源、路由、权限、状态与必跑项。确认这些事实后才选择改动，不用新建展示页冒充旧项目集成。

## 规范依据与沉淀

核对本次涉及的设计文档、`AGENTS.md` / `CLAUDE.md` 中的视觉段落，以及同类页面的生效 tokens、共享组件与实际画面。区分已确认目标、实现现状、历史记录及适用范围；页面用途、主题或断点不同不自动算冲突。冲突提示的时机按入口“开始前”，说明来源位置、具体差异、采用依据与范围。

遵守宿主的指令优先级与适用范围；本技能不能把有效的 Agent 指令降为参考，也不能仅凭代码覆盖它。视觉段落写在指令文件里，不等于已被确认是当前设计目标。以当前适用的明确决定确定目标、以代码核实现状；没有确认依据时，从运行页面和生效变量描述现状，整理为待确认草稿，不按数量、文件名或代码现状宣布规范成立。用户认可的页面可作该范围的提炼依据；Git 历史与时间只辅助区分旧记录。有效指令冲突无法在本次授权内消解，或无法判断且影响核心方向时，集中说明待决点再询问；其余工作继续。

用户要求整理规范时，先保留受影响原文，将确认有效的内容收拢到现有权威设计文档；没有合适位置才新增 `DESIGN.md`。获准整理的视觉段落改为该文档的链接，有争议的条目在文档内列为待确认，不能无声删除。保留工程、业务与授权约定，不将整个 Agent 指令文件替换成设计链接。标明适用范围、例外及原出处，核对旧入口能找到现行规范。

新项目或改版的代表页经用户确认，或达到用户已授权自行决定的验收条件后，从实际实现提炼后续页面需要的 tokens、组件用法、必要状态与响应式关系，记录代码位置与适用页面。优先更新同一份文档；单页偶然值、任务日志和落地页密度不提升为全项目规则。尚未确认的选择只写草稿。

整理或提炼时，在文档开头标注 `规范状态：草稿（待确认）` 或 `规范状态：已确认`，并写明依据、适用范围；混合文档将未决条目单列，不混入已确认允许值。按 [工具说明](tools.md#可选的设计规范比对) 写出该范围的 `oil-ui-tokens` 块，值来自可追溯的生效变量/组件及对应画面核对。只列有依据的字体、颜色、圆角、字号；缺项明示，不把全部计算样式收集成允许值，也不为消除命中扩大名单。

已有 tokens 块且工具可用时，可在开工核对中对代表页跑 `--design`；新提炼的块也用于检查提炼是否准确。先保留来源和原值，再查偏离，不能用本次页面反写允许值来证明自己合格。脚本不判断规范是否获批：对草稿只说“与当前草稿一致”，有确认依据才说“在已检查的四类值内符合已确认规范”；两者都不证明间距、密度、语义角色或审美合格。

## 截图诊断

从真实入口打开受影响页面，记录视口、角色、路由和业务状态。按图中区域编号指出问题、任务影响、依据及建议优先级；原截图与标注图分开，标注可用旁注/覆盖层，不能把标注写进业务 UI。仅诊断时业务文件保持原样，文件哈希/diff 是可复核依据。

偏离先分清四类：**缺 token**（缺少共同定义）、**一次性实现**（绕过已有组件）、**概念不一致**（同一状态/操作有多套含义）、**局部缺陷**（裁切、错位等）。修复顺序为任务受阻 → 缺少状态 → 流程层级 → 视觉动效 → 清理；精修不能偷偷变成重做。

需要 token 分层或组件变体的实现参考时，按需查 [资料检索](tools.md#按需检索设计与实现资料) 的 `implementation` 领域。

有成文 `DESIGN.md` 时，可用 `shoot.mjs --design DESIGN.md` 提示规范外字体、颜色、圆角、字号；只读取明确的机器可读 `oil-ui-tokens` 块，见工具说明。没有该块或只列部分类型时如实标覆盖缺口，不能靠猜 Markdown 判违规。

## 三档及独立的流程/功能范围

| 档位 | 可改变 | 默认保护 | 验收 |
| --- | --- | --- | --- |
| 整理 | 对齐、间距、字阶、已有控件状态、溢出、明确的文案问题 | 结构、设计方向、流程、数据与接口 | 同入口/同数据前后，任务没有新增步骤，细节问题可见修复 |
| 升级 | 获准的信息层级、组件使用、响应式、就地操作与反馈 | 品牌、已定流程/契约，未授权区域 | 主任务更清晰，多端/键盘和错误恢复走通 |
| 重塑 | 获准的视觉方向与页面骨架、整套相关页面 | 业务事实、权限/状态和未授权接口 | 新方向贯穿入口、详情、反馈与收尾；不是只改 hero |
| 流程调整 | 明确获准的任务步骤、分支与恢复 | 未授权的视觉与业务规则 | 同任务前后操作数/回退/异常恢复；少点一次不等于任务正确 |
| 新功能 | 获准的新入口、状态与集成点 | 既有任务和数据契约 | 新功能完成闭环，旧路径仍可用；不能重置旧数据换取演示 |

这些维度可组合，但一个“优化”请求不自动授权整页重塑或流程重做。已获准的强度直接执行，缺口只问会改变边界的事实。

## 在实际代码落地

- 复用业务对象与已有状态归属；避免复制第二份状态、替换真实 API 为 mock、注入演示路由。原型中的模拟状态工具不进入正式产品。
- 表单更换容器仍保留值、错误与权限；列表换布局仍保留筛选/排序/选择/返回；长内容与慢请求会暴露静态截图看不到的问题。
- 先存基线证据，再改受影响部分并检查相同任务。验收以结果、保护契约、必跑项与实际画面为据，不按修改文件数或审美分数推断成功。
- 本次形成可复用的设计决定时，按 [规范依据与沉淀](#规范依据与沉淀) 更新现有文档；日常局部修复不扩成全项目规范整理。

公开存量样例与三档改造的来源、冻结契约和运行入口见 [TodoMVC 案例](../assets/cases/todomvc/DESIGN.md)。历史验收证据随审计资料保存，不是日常任务必读；样例不代表任意用户项目已集成。
